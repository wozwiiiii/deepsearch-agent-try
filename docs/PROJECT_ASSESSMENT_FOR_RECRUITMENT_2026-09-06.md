## 一、市场对标：5 个真实校招 JD 的共性要求 vs 项目现状

对 2026 校招 5 个真实 JD（联想 AI Agent 开发、国家就业服务平台苏州 AI 智能体场景开发、苏州工业园区金融 Agent 算法、珠海 AI Agent 技术工程师、CSDN 岗位画像）做交叉比对：

| JD 共性要求 | 项目现状 | 匹配 |
|------------|---------|------|
| Python + FastAPI + async/await + 流式（SSE/WS） | 全有，且 WS 断线差量补发是自研 | ✅ 强 |
| LangChain/LangGraph 等框架落地经验 | deepagents（LangGraph ReAct）+ 自研主循环扩展 | ✅ 有，深度见下文风险 |
| 多 Agent 协同（主+子路由） | 主智能体 + 数据库/搜索/RAGFlow 三子智能体 | ✅ 有 |
| RAG（检索增强） | RAGFlow 集成（外部服务调用，非自建管道） | ⚠️ 有但偏浅 |
| **评估体系建设 / LLM Ops** | **45 条评测集 + judge 工具链 + 四轮对比报告 + 污染判定留证** | ✅✅ **差异化亮点** |
| 安全与合规 | 认证 fail-closed、租户隔离、限流、短时令牌（6/6） | ✅ 强 |
| **异步任务处理 / 任务调度 / Agent Runtime** | **P0-2 任务出进程未做（0/1）——任务在同进程 asyncio 内跑** | ❌ **最大缺口** |
| 可观测性（监控/指标） | 结构化日志有；Prometheus/OTel 无（1/2） | ⚠️ 半缺口 |
| Docker | MySQL 已容器化；应用本身未容器化 | ⚠️ 半缺口 |
| MCP 协议（2026 热点） | 未涉及 | ❌ 缺口（可选） |
| 向量数据库/K8s/vLLM | 未直接涉及 | ❌ 缺口（低优先级） |

结论：**在"框架应用 + harness 治理 + 安全"这条线上，项目已覆盖 JD 要求的 70% 左右，且评估体系是少见的差异化项；最大单点缺口是任务出进程（Agent Runtime/任务调度），其次是可观测性与应用容器化。**

## 二、你手里已经有的面试硬故事（资产盘点，不需要再写代码）

这些是已经发生、有数据、可验证的事实，直接转化为 STAR 素材：

1. **评测驱动的缺陷修复闭环**：45 条评测 → 发现三类真实缺陷（文件生成劫持、搜索内容超限触发 max_seq_len 400、主智能体早停）→ 分层修复（提示词劝 + 工具层硬约束 + 守卫续跑）→ 四轮验证 66.7%→80%→88.9%→91.1%。守卫累计 9 触发 9 救回。这个故事完整展示了"发现问题→定位根因→分层治理→量化验证"，是 Agent 工程岗面试最有说服力的主线。
2. **守卫的设计取舍**：为什么高精度低召回（宁漏判不误伤）、为什么区分过渡语/空输出/工具片段截断三种变体、为什么工具层硬约束而非只靠提示词——每个决策都有评测数据支撑，能扛住追问。
3. **安全层的完整设计**：认证 fail-closed、短时令牌替代 URL 密钥（并真实移除了兼容入口）、租户复合键隔离——对应 JD 的"安全与合规"。
4. **成本与稳定性治理**：run 级 + 会话级双层 token 预算、限流指数退避（数据：固定 70s 报废 2 条 → 指数退避 0 报废）、任务硬超时。
5. **真实工程韧性**（非代码）：.git 对象库损毁后的 reflog 重建、MySQL 容器事故导致的评测污染判定与重跑、限流窗口的污染留证——技术支持岗尤其吃这套"故障排查方法论"。

## 三、短板与风险（实事求是）

1. **任务出进程缺失是硬伤**：面试官问"长任务怎么保证服务重启不丢、怎么水平扩展"时，当前架构只能答"同进程 asyncio + 600s 超时"。这是中大型企业后端岗的必问题，也是项目"生产就绪"叙事的唯一断点。设计稿（TASK_QUEUE_DESIGN.md）已完备，未动手。
2. **框架深度依赖**：编排核心是 deepagents/LangGraph。定位必须诚实且主动："我在框架上解决了框架没解决的问题"（守卫、预算、回放都是框架外自研）——这个定位成立且有力；但如果被追问"不用 LangGraph 手写 ReAct 循环"，需要能讲清 agent loop、工具调用协议、状态机的基本原理（建议做一次白板推演练习，不必自研框架）。
3. **RAG 偏浅**：只集成了 RAGFlow，没自建过向量库/分块/重排管道。金融 Agent 类 JD 会追问 RAG 细节。若目标含 RAG 重的岗位，需补一个小型自建 RAG 实验或至少准备好"为什么选 RAGFlow 而非自建"的取舍论证。
4. **单人项目体量天花板**：无真实流量、无压测数据。表述时用"生产化演练"而非"生产系统"，避免被质疑夸大。
5. 通信工程专业背景：投技术岗需用项目与基础（数据结构/网络/OS 八股）弥补专业标签，项目评价体系（评测、熔断、安全）恰好是跨专业最有力的证明。

- ❌ K8s/vLLM/多模型路由：无真实流量驱动，堆砌关键词反而引火上身。
